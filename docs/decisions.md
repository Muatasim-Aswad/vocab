# Decisions

Non-obvious implementation choices and their rationale.

## Toolchain

- **mise owns Node and pnpm; `vp` comes from the project.** The global `vp` installed by mise's npm backend ignores the project's `vite-plus` and fails on `vp pack` ("TypeScript is not installed"). `mise.toml` adds `node_modules/.bin` to `PATH` instead, so the Vite+ version lives only in the catalog.
- **pnpm via mise's aqua backend, not `npm:pnpm`.** pnpm 12's npm package ships a placeholder that its install script replaces with the native binary; mise's npm backend leaves the placeholder, and pnpm fails to start.
- **Node pinned exactly in `mise.toml`.** `lts` moved with each release, so local, CI, and container runs could differ. The Dockerfile's base image uses the same version; upgrade both together. pnpm stays aligned between `mise.toml` and `packageManager` (corepack reads the latter in the container build).

## TypeScript

- **`typescript` 6.0, not 7.** TypeScript 7 has no stable programmatic API, and the NestJS 12 CLI requires `~6.0`. `vp check` already type-checks with the TypeScript 7 engine through tsgolint.

## Vite+

- **`vite` and `vitest` overrides in `pnpm-workspace.yaml`.** Required by Vite+ for manual setups: `vite` aliases `@voidzero-dev/vite-plus-core`, and `vitest` is pinned to the version Vite+ bundles, so dependencies share one copy. Upgrade them together with `vite-plus` (`vp migrate` does this).
- **`peerDependencyRules.allowedVersions.vite: "*"`.** The alias reports Vite+'s version (1.x), which fails peer ranges like `^8` although it contains Vite 8.
- **`build` and `test` are Vite+ tasks, not `package.json` scripts.** Vite+ caches tasks by default and scripts only with `run.cache.scripts`, which would also cache `e2e`, `dev`, `arch` and `db:*`, whose results depend on servers, databases or deliberate probe writes. Tasks track the files each command reads (including another package's `dist/`, so an API rebuild reruns the CLI tests) and restore written files on a hit. The API build excludes `dist/` and `*.tsbuildinfo` from inputs because Nest reads its previous output while rebuilding.
- **Lint and format config only at the root.** `vp check` ignores package-level `lint`/`fmt` blocks.
- **Package `dev` uses `vp pack --watch --no-clean`.** Watch mode otherwise empties `dist/` on start, and the apps (started in parallel) fail to resolve the packages.

## Packages

- **Contracts are built, not consumed as source.** The API runs compiled JS on Node, which cannot load another package's TypeScript; building with `vp pack` lets every app import the same output.
- **`@vocab/api-client` is its own package.** Web now and the CLI later share one HTTP client: contract paths, auth header, response validation, and error parsing. It holds no backend code.
- **`ValidationIssue` is `{ path, message, code? }`.** Validator-neutral (Standard Schema issues have no `code`); Zod's own issues are not sent as-is because they can carry submitted input and non-JSON values. Paths start with the request part (`body`, `query`).
- **Build scripts:** `better-sqlite3` is allowed (native driver); `esbuild` (via drizzle-kit) is denied, as its optional platform package already provides the binary.
- **Drizzle 1.0 RC.** Drizzle's docs recommend the 1.0 RC for new projects.

## API

- **Route contracts drive the API.** `@Contract(routes.x)` sets method, path, auth, request validation, and response validation/stripping from `@vocab/contracts`, and OpenAPI is generated from the same objects, so the served document cannot drift. A hand-built OpenAPI 3.1 document replaces `@nestjs/swagger`, which needs DTO classes instead of Zod schemas.
- **Default-deny auth.** The global guard requires bearer or an opaque browser session according to each route's contract; handlers without a contract fail closed.
- **One log line per request.** Middleware logs each request on close; the error filter only records failure details for it. Framework error messages go to `internal` with query strings removed; public messages are fixed per code.
- **Explicit migrations, existing database only.** The server opens the SQLite file with `fileMustExist` and never migrates; `migrate.ts` (compose's `migrate` service) creates and migrates it. Readiness compares Drizzle's history with the shipped files by name and hash, so edited or missing migrations surface as `diverged`.
- **Feature-owned domain tables.** The first new migration creates vocabulary, study memory/session, auth session, mutation receipt, and import receipt tables. The former SQLite migration files were never part of the new migration history. The entry allocator starts at zero on an empty target and was set to the imported high-water mark before publication.
- **Completed legacy cutover.** The one-time database snapshot and import tools used a source fingerprint, staged and verified a complete target, and were retired after deployment. Their cutover harness was removed. The applied migrations and `legacy_import_receipt` table remain because deployed databases still contain them; the receipt schema lives in `infra/db` because no feature owns this historical table. Server startup never migrates or imports.
- **Revision and study state.** Imported entries begin at revision 1. Vocabulary edits/deletes can require an expected revision; study sessions persist JSON state with a revision precondition so an interrupted session can be recovered without repeating a review. Final study history retains schema-v2 fields in SQLite.
- **Study reviews never change the entry.** Memory lives in the study-owned `study_memory` table, and a review writes only that row, in one statement that also requires the entry to be active at the revision the session read; an entry edited mid-session refuses the stale review with a conflict. Entry `revision` and `modified_at` therefore change only with content (add, edit, stub completion, meaning-label backfills), so reviews never conflict with an open Edit and `GET /api/entries?order=modified` lists real edits (`order` also takes `added`, the default, and `alphabetical`). Values written before this change may still carry study-review times.
- **Entry IDs are integers.** Existing vocabulary entries keep positive safe-integer IDs (`entryId`); `uuidV7` is for new record types such as sessions and mutations.
- **One owner, bearer CLI and cookie web sessions.** One server-configured personal token (≥ 32 characters) authorizes CLI bearer requests and a browser login exchange. The server stores opaque sessions durably without idle or absolute expiry; logout revokes one and token rotation revokes all. A finite persistent HttpOnly/Secure/SameSite cookie is renewed during authenticated browser use. HTTPS and configurable host/origin rules are required remotely; loopback HTTP gets only a narrow development cookie setting. The browser never stores the token/session in localStorage. This supersedes the scaffold's per-request web bearer prompt. Rate limiting is not added: a random 32-character token is not guessable, and concurrency is bounded.
- **Atomic mutation receipts.** UUIDv7 identities share one SQLite receipt table; canonical request hashes reject changed-content reuse, and completed retries return the prior response. Vocabulary and study writes commit their state with the receipt in one transaction. AI generation shares an in-process identity map while pending and stores successful drafts for later retries.
- **Study session retention.** The API retains abandoned durable sessions and reviews indefinitely; an explicit end stores the final history record. No background cleanup deletes study history. A later retention policy may archive ended sessions only after verifying their history records.
- **Vocabulary/study import boundary.** `dependency-cruiser` permits only the shared vocabulary/study model types, schema foreign keys, normalization helper, and Nest module wiring across those feature directories. Runtime operations still cross through services; all other cross-feature internals remain forbidden.
- **SQLite owns study history.** This supersedes server JSON study logs and `STUDY_LOGS_PATH`. `study_history` holds one immutable schema-v2 document per final record, with derived columns (start/end, outcome, review count) for bounded keyset listing; the session row stays the working state and the history row is the final fact. Ending a session updates it and inserts the history row in the transaction that stores the mutation receipt, so a failure leaves none of them and a lost response replays after restart. History IDs are a new session's UUID or an imported log's own `sessionId`, so exports never assume UUIDs. Entry IDs in documents are historical references without foreign keys; vocabulary deletion cannot remove history. Triggers reject updates and deletes of history rows and imported source bytes. Operators back up only the SQLite file.
- **explicit, lossless JSON import.** `db:import:study-history` validates every file against the shared schema-v2 contract (unknown fields kept, nothing coerced) before one transaction writes records, exact source bytes (deduplicated by SHA-256) and the full input report as provenance. A log matching an existing ended session must equal the session's stored state except for the outcome, which it supplies; a disagreement, an open session, divergent content for one identity, malformed or unsupported input, symlinks, non-JSON entries or a source change during import refuses the whole import. Identical retries write nothing. Ended sessions without a log are reported, never given a guessed outcome. The apply takes SQLite's exclusive lock, which fails while the API (or any connection) has the database open. The source fingerprint uses the historical log-tree digest.
- **API serves the web build (`VOCAB_WEB_ROOT`).** One origin and one container for personal deployment: no CORS in production, and the browser test exercises the deployed topology. The HTML gets a strict CSP, so the web app sets Zod's `jitless` mode (Zod otherwise probes `new Function`).
- **Portable container storage defaults to a named volume.** Compose creates `vocab_data` with the image's runtime ownership, shared by the API and explicit migration service. `VOCAB_IMAGE` selects their common image; source builds and prebuilt images use the same file. Existing bind-mounted data must be migrated deliberately before switching storage. The API still opens only a migrated existing database.
- **Generic Docker instructions are tracked; host notes stay private.** `docs/deployment.md` describes portable build, image selection and storage operations. Private host settings and the former operations runbook remain in ignored `docs/migration/*.local.md` files.
- **Architecture checks include client access to AI and CLI persistence.** The dependency graph excludes built workspace outputs but retains third-party `dist/` targets, because excluding every `/dist/` hid `@google/genai` imports from negative probes. Test-only web helpers live outside production `src`; runtime functions used only by tests are no longer exported.
- **Sense-label backfills carry revisions.** Both clients send the revision they saw for each existing meaning; the API checks it inside the create transaction before changing any label. This closes the race after the web's preparation refresh and gives the CLI the same stale-write protection.
- **Stubs show the words related to them.** Relations are stored in both directions, so a stub always has related words; list rows (search, list, prepare matches) carry them for stubs only, resolved in one batched lookup per page, since a stub has no word type or example to show. Status moves to the entry details panel instead of a "term only" note.
- **Captures are separate from entries.** A captured term records an intent to complete a word later, without claiming that it has the same sense as a matching stub. Captures have no study memory or relationships and never appear in vocabulary search or study. The capture routes deduplicate case and whitespace variants of one term; list offers exact-term lookup and a normalized prefix filter (LIKE wildcards taken literally, same newest-first cursor) for search affordances. Entry create/update can consume a capture in the mutation-receipt transaction only when the resulting active entry has the same parsed lemma. A stub is completed by updating its existing entry ID, preserving its relationships.
- **Search history is an append-only server log.** Recent searches are shared by web and CLI, so they moved from browser `localStorage` to SQLite (`search_history`); old local lists were not migrated. Clients send a UUIDv7 and a UTC time with each search, so retries insert nothing new and need no mutation receipt, and devices never conflict because they only append. Reusing an ID with different content is a conflict. Times more than 5 minutes ahead of the server are rejected, because one far ahead would pin a term or hide later searches. Clear appends a row to `search_history_clears`; the list shows distinct terms (`term_key`, lowercased in JavaScript, since SQLite `lower()` folds only ASCII) searched after the latest clear, newest first, in their latest spelling. Triggers reject updates; rows are kept (about 100 bytes each), and deletes stay possible for a later retention rule.
- **AI draft booleans stay in the exchange contract.** The legacy prompt emits top-level `irregular`, `separable` and `uncountable`. The API returns them instead of stripping them, and the CLI maps them into its existing structured Add defaults. No live model-quality claim follows from fake-provider tests.
- **AI audit evidence lives in SQLite.** A request binds its full validated input to its existing UUIDv7 identity, including sense hints; failed retries add executions, while successful receipt replays reuse the original generation and draft IDs. Immutable prompt configurations, raw provider envelopes and text, per-call outcomes, and validated returned drafts remain available for later evaluation. The prompt hash covers the selected instruction, input-layout version, response schema, settings, and validator version; each attempt also stores the exact non-secret rendered request. Entry create/update can carry draft IDs, and the server stores the submitted write, previous entry for updates, and committed entry revision in the write's receipt transaction. Presented and skipped events mean only that the API received those reports; no event means unknown. Historical AI receipts predate the audit and replay without invented IDs or missing provider evidence. Audit data is private application data retained with the database until an explicit retention policy exists.
- **AI quality is judged by manual live evals, not tests.** Model output varies between identical calls, so fake-provider tests prove plumbing only. `apps/api/evals` runs the app's real prompt modules and generation settings (one `generationSettings` source shared with the provider), or variants of them, against Gemini, and saves every output. Only exact facts are checked by code: forms as sets against references from woordenlijst.org, flags, labels. Meaning quality is graded per word by an isolated frontier agent through the machine's `local-agent` command, blind to variant names, as yes/no and coverage checks rather than scores, because numeric scores drift between calls. Each word is graded with all variants side by side: comparison is steadier than judging one output alone, and one call per word keeps attention focused and failures retryable. Sense references are tiered (essential, valid, uncertain) because sources disagree on how finely to split meanings. Gemini 3.8 Flash serves generation and meaning matching (2026-10-03): with the eval-tuned prompt it covered every essential sense and gave exact verb forms at about $8 per 1,000 words and 8 s per word, while Flash-Lite missed senses and broke the meaning-match label rule; high thinking would also have split rare fixed-expression senses but costs 3.5 times as much and takes 25 s.

## CLI

- **Fast mode captures instead of creating.** A fast-mode term becomes one `createCapture` write through the pending-write journal, so a lost response is retried with the same identity and needs no preparation, sense choice or prompt. Normal and detail Add are unchanged; `captures` pages through captured terms by walking the API cursors from the start, like `list`.
- **Searches are recorded outside the journal.** Each search sent with Enter is recorded in the background while results load; the command waits for it only before returning, so a one-shot run does not exit first. The pending-write journal replays in order and holds later writes behind an unconfirmed one, so a lost history entry must not block vocabulary writes; a failed record is dropped.
- **AI forms win over inferred forms.** JSON and AI Add keep the given forms when they hold the same words as the inferred ones in another order; a real mismatch asks, with Keep provided forms first. Inferred forms come from spelling rules and miss irregular and context-dependent forms, so they never replace a model's answer by default. `formsConflict inferred` remains an explicit opt-in.

## Tooling

- **dependency-cruiser and knip.** dependency-cruiser enforces app, package, and API layer boundaries and cycles; knip reports unused files, exports, and dependencies, and `knip --production` catches exports only tests use. `scripts/verify-architecture.ts` writes forbidden probe files, asserts both tools reject them, and deletes them.
- **Docker caches downloads, never build output.** The pnpm store is a BuildKit cache mount (`pnpm_config_store_dir`; pnpm 12 ignores `npm_config_*`), and pnpm checks each package against the lockfile, so reuse cannot change the image. The Vite+ task cache stays out of the image: the server builds production images itself, a wrong hit would ship stale code, and `--no-cache` would not clear it. CI keeps Docker layers in the GitHub Actions cache (`mode=max`); that affects only CI's build check.
- **Playwright smoke test against built artifacts.** It migrates a temporary database, starts `apps/api/dist/main.js` on an ephemeral port serving `apps/web/dist`, drives Chromium, and requires a graceful shutdown. Component tests (happy-dom) cover UI states only.

## Web app

- **PWA caches only the built shell.** `vite-plugin-pwa` (`injectManifest`, `apps/web/src/sw.ts`) precaches the HTML, JS, CSS, fonts and icons and answers navigations with the shell, so the installed app opens offline and shows its "could not be reached" state. API requests bypass the worker: study and vocabulary data is never served stale, and writes are never queued offline.
- **New worker takes over immediately, without reloading.** An installed app rarely closes every window, so a waiting worker would keep an old shell against a newer API. Safe only while the build is one eagerly loaded bundle; code splitting would let an open old page request chunks the deploy removed.
- **Add links an exactly captured term and removes it on save.** A term from a capture, or a typed term with an exact capture, sends the capture with the save, without a choice: a capture rarely names a different meaning, and recapturing it is cheaper than a switch on every save. The API alone decides whether the entry consumes it (same parsed lemma, active result). When it refuses the capture (removed meanwhile, or the word was changed), nothing was written, so Add resends the same entry without it under a new mutation ID and says the capture stays. The browser never deletes a capture after a save.
- **Add resolves the term before showing fields.** Add first shows only the term; Enter or its + icon checks it. Any existing meaning, stub or not, is shown as a result card with an edit icon, plus Add another meaning. Editing opens that entry's Edit page. Add another meaning first asks only for the meaning labels, each beneath its card; the new meaning is the last card, in place of the term field, showing the typed term or what an AI suggestion holds, since AI may correct the term into one that already has meanings. Continue replaces the choice with the fields, where the new label stays editable, and a label or changed-meanings failure reopens the labels. A new term shows the fields at once. Changing the term starts over.
- **Add warns when a term is another entry's form.** Preparation also returns `formOf`: other entries whose stored forms include the term, so an unnormalized form ("liep" of "lopen") is caught before it becomes a separate word. It is advice, not a server rule, because a real word can look like another's form. Add shows those entries as cards with Proceed (add the term as its own word), Edit (open that entry) and Cancel (end the add). AI suggestion terms skip it: the model names the word itself.
- **AI suggestions can complete an existing meaning.** When AI corrects a term into one with meanings the user has not seen, the user first says whether the suggestion is one of them (Same meaning) or another (New meaning), since the old entry may only have been too incomplete to match the typed form. Same meaning edits that entry at its revision through the ordinary update, with the AI provenance: a stub is completed and shown as the entry to accept; an active entry opens in the form with every value the suggestion holds winning, a note under each field it replaced showing the old value, forms replaced, and examples, collocations, tags and relations combined. Empty suggestion values never clear the entry. No merge route is needed for this; merging two existing entries is still unsupported.
- **AI recommends same or new meaning; the user decides.** `POST /api/ai/meaning-match` takes a candidate meaning (term plus notes or an example; the term alone cannot be compared) and the IDs of entries sharing its lemma, which the server loads itself, each with its relations as type, related term and that entry's label, since for a stub they are the only evidence of its meaning. It returns "same" with an entry ID, or "new" with a Dutch label for the candidate and for exactly the unlabeled entries, a reason, and the revisions compared. The server rejects model output that breaks the label rules (one or two words, not the term, all labels of the term distinct, existing labels kept) rather than repairing it. It is read-only, audited like generation (`ai_meaning_matches` holds the validated decision) and replayed by request ID. Comparison is a separate request, not part of generation: generation stays one job, only suggestions that meet unseen meanings pay for it, and a replayed generation never returns a decision about entries that changed since. The web uses it only for AI suggestions: manual adds hold no meaning to compare, and the user writes the labels that tell meanings apart. Later suggestions are compared in the background; an opening suggestion waits in the AI busy state ("Comparing…") so its choice screen appears once, with the recommended button highlighted and the reason in the AI status beneath the action bar ("“Same meaning” is recommended: …"). A "new" recommendation fills the labels the user has not changed. A recommendation counts only while the compared revisions are current; a failed comparison leaves the choice to the user. Ambiguous recommendations remain a user decision; validate matching quality with live evals before changing the prompt.
- **Edit has its own address and draft.** `/entries/:id/edit` edits one entry; the entry page's Edit icon and Add's "Edit this entry" both lead there, the latter taking a reviewed capture along and clearing the Add draft. Add and Edit keep separate in-memory drafts, so an open edit never blocks adding and vice versa. Each visit rereads the entry unless its draft holds changes; unsaved changes to another entry are kept until the user continues or discards them. Cancel returns to the entry; saving returns to Search (see below). The term is not editable there, since only a stub's edit sends it.
- **A successful save returns to Search with a toast.** Add and Edit clear their draft, replace the form in history with the last search, and confirm the save in a toast (with the kept-capture note when relevant), so no result screen has to be dismissed. The toast comes from the store's save callback, so it shows even if the user left the page while saving. The one exception: after saving an AI suggestion with others still undecided, Add stays and opens the next one; skipping the last one also returns to Search. Rejected saves keep the filled form with field errors or a notice.
- **Editing an entry is an update of its ID with every field.** Edit mode fills the fields from the entry and sends all of them, so emptied fields are cleared and relation tokens replace its relations; grammar values it leaves unset go as `null` or `false`, which the API treats as clearing. A stub's edit also sends the term, a lexical change that promotes it, and keeps API suggestions for fields it lacks; an active entry's values are the user's own. A meaning label is required only when other meanings of the term exist. Phrase type cannot be cleared, because the contract accepts only a valid value.
- **Add shows every field, with pinned actions, and suggested forms as removable chips.** There is no "More details" disclosure or inferred summary; Add and Edit keep their actions in a header pinned to the top (`position: sticky`), so the site footer stays. Text actions come first and icon-only actions last (Add: Save, Cancel, then Clear, Keep draft and AI), so text and icons never alternate; AI is the one button with both an icon and text. Clear needs no confirmation. Notes open behind a button unless the entry has notes. API suggestions fill untouched word type, grammar and tags. Suggested forms show as outlined chips, saved unless removed; for an entry that already has forms they stay behind a Suggest icon, so editing never adds inflections the user did not ask to see. Forms, collocations and tags are chips beside their label, with the input behind an Add icon after the last chip; help text sits behind info icons.
- **AI suggestions are reviewed as entries before any form.** AI starts only on request: from the bar, from an icon beside Continue in the term field, or from Search when nothing matches. A term with meanings first shows them, and AI is asked once Add another meaning is chosen; editing an existing meaning goes to Edit without AI. While AI works no form shows. Each suggestion appears as the entry it would save (`savedEntryFields`, the same values Save sends) with Accept, Skip, Previous/Next among undecided suggestions, and Edit, which opens it in the form, where Accept becomes Save and Edit disappears; there is no Cancel or Clear in the AI flow. Accept adds related words that are not saved yet as new entries, since the suggestion already shows them; one that fails validation or has a related word matching several meanings opens the form with the errors. Network, sign-in or lookup failures keep the suggestion under review with a notice, and Accept tries again, rechecking related words whose lookup failed. Skipping the last suggestion returns to Search and keeps the user's own draft only when it holds more than the term. Changing the term while AI works drops that request, so late suggestions never replace the new term.
- **Recent searches are recorded when focus leaves the search field.** Typing, Enter and Clear keep focus in the field and record nothing, so partial words do not appear; a click, tap or Tab elsewhere records the field's text. Clear keeps focus in the field on press, and a window losing focus is ignored. The web reads the server's 50 most recent distinct terms (see search history under API); a recorded term shows at once, is sent without waiting, and a failed send is dropped when the list is next read. Empty Search shows the first 5, with All searches opening `/search-history`, which lists all 50 and is the only place to clear the history. Below them, empty Search shows the 10 active entries whose content changed most recently, new ones included (linking to their pages, with All entries opening `/entries` in that order) and the 5 newest captures (opening their search, where they can be added or removed), all as chips. `/entries` lists every active entry with Search's result cards, ordered newest, recently changed or A–Z (lemma, ASCII case-insensitive) and filtered by the same type filter; both live in the URL. A filter that matches nothing is shown as an empty list, although the API answers it with not found.
- **Search shows captures only when no entry matches, except an exact capture.** An exactly captured term is shown as its Captures row (first in the results list, or alone when nothing matches); with no results and no exact capture, Search offers Capture for later, Add and AI, and lists captured terms starting with the query. Each of those actions empties the search, also for the return from Add, since the word is then handled; a capture is confirmed in a toast. Captures have no detail page.
- **The build knows its commit; the server says which build it has.** The `build-info` Vite plugin (`apps/web/build-info.ts`) bakes revision, commit time and build time into the bundle and emits the same record as `/version.json`, served `no-store` and never precached or answered with the shell. srvr passes them as the `APP_*` Docker build args, because the build context excludes `.git`; a local build reads git, and with neither the revision is `dev`. Local builds use `dev` for tracked or untracked Git changes; the web build task is uncached so Git identity cannot replay across source changes. Explicit build arguments are trusted for clean or Git-free build contexts and must describe the exact supplied source. Supplied timestamps are used verbatim; without a build time, the current time is used. Menu → Version (`/version`) shows the running build and, when `/version.json` names another revision, Reload, which asks the worker to update first. The first run of a new build on a device shows a one-time toast linking there (`vocab.seen-revision` in local storage); first visits and blocked storage show nothing. There is no reload prompt beside it, since the worker already takes over immediately (above).
- **Tailwind CSS 4 with tokens in `@theme`.** Every color, size, weight, width and shadow is a token in `apps/web/src/app/styles.css`, so utilities name design values (`text-supporting`, `font-term`, `max-w-reading`) and arbitrary values stay for one-off geometry. Colors switch to dark by redefining the same variables, from the device setting or the footer menu's `data-theme`, so components need no `dark:` variants. The default palette and type scale are cleared: text sizes carry no line height, matching the earlier stylesheet where text keeps its block's 1.5. Form controls, headings, links and `mark` keep element base styles in `@layer base`, since nearly every one looks the same; buttons do not, because links share their look, so they take the `control` class list instead. `cn` is tailwind-merge told that text sizes never replace a `leading-*`. Results' terms carry `data-testid="term"` as the one test hook, since no role singles them out.
- **Icons are rendered from SVG sources.** `public/icons/vocab.svg` (rounded, `any`) and `vocab-maskable.svg` (full bleed, mark inside the safe zone; also the iOS icon) render the PNGs with `rsvg-convert -w <size> -h <size> <svg> -o <png>`.
